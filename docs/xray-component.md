# Компонент Xray для XHTTP-прокси

Серверный компонент поддерживает **Xray-core v26.10.31**. Релиз закреплён по [upstream tag](https://github.com/XTLS/Xray-core/releases/tag/v26.10.31), коммит `a4a3dff`. Перед каждым новым запуском `XHttpHost` вызывает `xray version` и проверяет точный номер. Проверка номера не заменяет проверку происхождения и контрольной суммы бинарника при упаковке.

## Интеграция

`AmneziaGeo.Server.Routing.XHttp.XHttpHost` создаётся с каталогом конфигураций, путём к проверенному исполняемому файлу и `ILogger<XHttpHost>`. Один экземпляр обслуживает желаемый список прокси через `ApplyAsync`; `State(id)` возвращает состояние конкретного дочернего процесса.

`XHttpProxy.Port` обозначает **внутренний HTTP-порт на 127.0.0.1**, а не публичный порт CDN. `Path` содержит один URL-сегмент, `Credentials` содержит непустые GUID пользователей VLESS. Пользователи нормализуются, сортируются и удаляются дубли. Пустой набор пользователей возвращает ошибку этого прокси и останавливает его прежний процесс; listener без авторизации не запускается. Остальные записи продолжают применяться.

Компонент создаёт отдельный процесс `xray run -c <file>` на прокси. Неизменный нормализованный конфиг не перезапускает живой процесс. Завершившийся процесс запускается при следующем `ApplyAsync`. Изменившийся или удалённый listener останавливает только процесс, созданный этим экземпляром. Завершение убивает его дерево процессов и ждёт до пяти секунд; системные службы, systemd и чужие процессы не используются. Повторный `DisposeAsync` повторяет остановку, если предшествующая попытка не завершила процесс.

Конфиги пишутся атомарно, новые Unix-файлы имеют режим 0600. Вывод процесса ограничен по объёму и не передаётся в logger. Диагностика завершения возвращает код и текст с удалёнными GUID; ошибки операций логируются с объектом исключения. Владельцем каталога и Windows ACL занимается установка/служба приложения.

ServiceServer подключает компонент к общему фронту. XHttpRefresh раз в секунду обновляет список клиентов из действующих шаблонов и восстанавливает завершившиеся процессы. Чтение пользователей и применение сериализованы отдельным gate. Изменение пользователей перезапускает только процесс соответствующего XHTTP-прокси и завершает его прежние соединения. Соседние WebSocket и XHTTP процессы продолжают работу. Если остановка не удалась, fault сохраняется; новую копию на тот же listener компонент не запускает.

Запись каталога хранит публичный Port отдельно от ListenPort (0 означает Port). OriginHttp разрешает обычный HTTP только для пути XHTTP. Например, клиент использует cdn.infobar.info:443, а сервер слушает HTTP80. Эти серверные настройки не публикуются в hello. Даже на общем порту панели HTTP не открывает панель, hello, подписки и WebSocket. Проверка использует фактический TLS connection feature, включая случай доверенного X-Forwarded-Proto.

## HTTP и UDP

Генерируется VLESS поверх XHTTP `packet-up`, `uplinkHTTPMethod: GET`, `uplinkDataPlacement: header`. Batch ограничен 2048 байтами до Base64, отдельный заголовок также ограничен 2048 символами, padding имеет диапазон 100–100, общий лимит заголовков Xray 8192 байта. TLS завершается публичным фронтом/CDN; внутренний listener использует обычный HTTP.

Сервер не привязывает вход к одному UDP-назначению: VLESS передаёт целевой адрес и порт, заданные клиентом. Freedom явно разрешает UDP, включая loopback и приватные адреса; остальные сети запрещены. Это необходимо для локальных WG/AWG-интерфейсов и назначения на другом хосте. Доступ к listener контролируется GUID пользователей; ограничения назначения при необходимости задаются над этим компонентом.

Клиент должен использовать тот же путь, `packet-up`, GET/header и согласованные padding/размеры. При небольшом batch штатный клиентский интервал 30 мс ограничивает upload; для первичного прогона подходит 1 мс. Публичный Host может отличаться от Host запроса к origin, поэтому серверная проверка Host не задаётся в генерируемом JSON. Фронт должен сохранять полный путь, включая добавляемые session/sequence, и заголовки `X-Data-*`.

Для проверенного ресурса cdn.infobar.info клиент использует TLS ALPN h2 и fingerprint unsafe (стандартный GoTLS с проверкой сертификата). CDN-origin остаётся HTTP/1.1. При H1 между клиентом и CDN малый ответ в проверке задерживался до timeout; при H2 через production front вернулись пакеты 33, 148 и 1280 байт. Фронт приложения принимает TLS HTTP/2 и HTTP/1.1 на общем порту. Это не HTTP Upgrade. В Xray v26.10.31 allowInsecure запрещён; необязательный явный pin передаётся строкой pinnedPeerCertSha256 из 64 hex-символов.

Обратный канал остаётся потоковым ответом на GET. Xray выставляет `Cache-Control: no-store`, `X-Accel-Buffering: no`, SSE content type и вызывает flush; это не гарантирует, что конкретный CDN не буферизует ответ. В ресурсе Yandex CDN необходимо отключить кеширование туннельного маршрута и проверить передачу заголовков, потоковую отдачу и таймауты. Режим query-параметров «не кешировать» сам по себе не выключает кеш CDN.

## Лицензия и поставка

Xray-core распространяется по [MPL-2.0](https://github.com/XTLS/Xray-core/blob/v26.10.31/LICENSE). При включении бинарника сохраняются лицензия и необходимые уведомления, указывается версия и доступ к соответствующим исходникам. Изменения исходных файлов Xray при их распространении предоставляются на условиях MPL-2.0. Сторонние зависимости Xray имеют собственные лицензии, их уведомления должны войти в поставку.

deploy/xray.sh загружает закреплённые архивы linux-x64 и linux-arm64, сверяет SHA-256 и извлекает только исполняемый файл, LICENSE и README. Native publish и Docker включают их в поставку. Установка хранит компонент внутри версии приложения, Docker в /usr/local/bin. XHttp:Executable и XHttp:Directory задают пути; штатно используется бинарник рядом с приложением либо xray из PATH.

В репозиторий не помещаются бинарники, рабочие конфиги с GUID, журналы процесса и пользовательские данные. Поставка закрепляет версию и SHA-256 каждого целевого архива. Совместимость с Yandex CDN подтверждается отдельным живым прогоном, а не проверкой JSON или номера версии. Сквозная проверка настоящих WG/AWG и платформенных клиентов остаётся AG-693.
